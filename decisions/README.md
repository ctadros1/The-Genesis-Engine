# Architecture Decision Records

ADRs record consequential architecture, compatibility, performance, security, and operations choices. The current ADRs are candidates with Status: Proposed. Do not treat them as final until their evidence requirement and applicable user approval are satisfied.

## Lifecycle

1. Create a proposed ADR before or with a durable design choice.
2. State context, credible options, proposed choice, consequences, performance/operations impact, compatibility, and revisit condition.
3. Link tests, benchmarks, spikes, or live audit evidence.
4. Mark Accepted only after evidence and required approval; mark Superseded rather than erase history.
5. Update docs/22-decision-log.md in the same change.

Use adr-template.md for new records. Keep rule/config changes that do not alter architecture in the Rule-Change Ledger unless they cross a durable design boundary.
